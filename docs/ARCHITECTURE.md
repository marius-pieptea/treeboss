# Architecture

```
trb (CLI) ──HTTP/SSE──▶ daemon ──spawn──▶ claude -p … / codex exec … / cursor-agent -p …
                          │                     │
                          │                     └─ MCP stdio ─▶ trb mcp-serve ──HTTP──┐
                          ◀───────────────────────────────────────────────────────────┘
                          └── SQLite (~/.treeboss/trb.sqlite), worktrees/, cli-mcp/, skills/
```

## Modules (src/)

| path | what it owns |
|---|---|
| `engines/registry.ts` | One `build(input) → {cmd,args,stdin,env,cleanup}` per engine; MCP rendering (claude file, codex `-c`, cursor workspace file). |
| `engines/stream.ts` | NDJSON → progress lines, final answer, session id, usage. claude, codex, cursor, agy, opencode shapes. |
| `engines/runner.ts` | Spawn in its own process group, idle/ceiling deadlines, abort, success/failure decision, refused-resume detection. |
| `git/worktree.ts` | Prepare (replay dirty state as a baseline), finalize (commit, `wip:` on failure), cleanup, sweep, `mergePatch`. |
| `sessions/manager.ts` | Leads and subagents in one table; turns; resume and the replay fallback; caps; ownership; merge; recovery; reaper. |
| `sessions/tools.ts` | The seven `subagent_*` tools: definitions and `executeSubagentTool`. |
| `sessions/hub.ts` | In-process pub/sub the SSE stream follows. Persistence is the `events` table, so late clients replay then follow. |
| `mcp/serve.ts` | The stdio MCP shim. Stateless; forwards to the daemon with `x-trb-session`. |
| `mcp/store.ts`, `skills/store.ts` | The registries, and per-run materialisation. |
| `attachments/` | One view over what a session has attached: specs and plans (`session_specs`) and docs pages (`session_docs`) stay in their modules, this decides which a path is (by where it lives), lists them together, builds the single `# Attached project files` block a turn receives, costs it, and names it in a handoff. |
| `specs/` | The Specs module: `tasks.ts` (tolerant tasks.md parser, one-character writer), `store.ts` (features and status derived from the files, path guard), `attach.ts` (`session_specs`: links only; prompt blocks; checkbox bookkeeping after a turn), `implement.ts` (steps, goal-mode implement, parallel heads, one task, architecture), `prompts.ts`, `templates.ts`. |
| `roadmap/` | The Roadmap module: `format.ts` (parse and minimal text edits of ROADMAP.md; every other byte is preserved), `progress.ts` (spec task counts, link validation; deliberately separate from `specs/tasks.ts`), `store.ts` (the view, atomic writes with an optimistic `rev`, two small tables for the file path and item sessions), `sessions.ts` (start a spec or build session from an item). |
| `checkpoints/` | A snapshot of a session's working tree after every turn, as a commit in `refs/trb/checkpoints/<session>/<turn>` built with a private index (no branch, HEAD, real index or stash is touched). `store.ts` snapshots, lists, prunes and rewinds (files only, after saving the current state as an `undo` checkpoint); `fork.ts` rewinds a session or opens a new isolated lead at a turn's commit. |
| `verify/` | After a turn: detect (`typecheck`/`lint`/`test` from package.json, Cargo, go, Python, or the workspace's own list), run (process-group kill on timeout), `loop.ts` (failures go back to the agent as the next turn, bounded; a session is `done` only when the latest turn's checks passed; goal mode will not call a goal met while they fail), `store.ts` (global > workspace > session settings, runs). |
| `treeboss/` | Treeboss mode: `store.ts` (per-session on/off, tier and who set it, fix count, delivered flag, last check; falls back to `treeboss_mode`), `rules.ts` (the block the agent is told), `gate.ts` (checks after each turn), `research.ts` (the area tier's research steps). |
| `hydra/pairs.ts`, `hydra/roles.ts` | Pair CRUD, the lead contract, the 12-role library. |
| `daemon/server.ts`, `daemon/lifecycle.ts` | The HTTP API, SSE; start/stop/status and recovery. |
| `cli/` | Thin clients. Config commands edit SQLite directly (the daemon reads it every turn). |

## The factory

The factory turns a spec into a shipped app and feeds what happens back into the roadmap. Each piece is a module with its own tables, created lazily on first use (`CREATE TABLE IF NOT EXISTS`, additive, like the roadmap's). Routes live in `daemon/routes/`, CLI clients in `cli/commands/`.

| path | what it owns | tables |
|---|---|---|
| `products/` | `store.ts`: products (the thing you ship: status, monthly budget) and their repos (workspaces attached). `cost.ts`: spend per workspace and product, summed from `turns.cost_usd` over the sessions cut from each folder (the most specific workspace wins, UTC months). `portfolio.ts`: one view of every product with roadmap progress, last verify and spend. | `products`, `product_repos` |
| `autopilot/` | `runner.ts`: a run over a spec's open tasks, one at a time: a session per task, check, tick, then the operator's gates (`approve-every`, `approve-merge`, `approve-tagged`). `schedule.ts`: cron jobs (`prompt`, `lab_sweep`, `verify`, `deps_update`, `signals_sync`) and the ticker that starts them. | `autopilot_runs`, `schedules` |
| `secrets/` | `crypto.ts`: AES-256-GCM, one 32-byte master key at `<home>/secrets.key` (0600), a fresh 12-byte IV per value, and the workspace, environment and name as associated data, so a copied ciphertext does not open. `store.ts`: environments (dev, staging and prod always exist; custom ones are added), secrets as ciphertext, `resolveEnv` (plaintext, server-side only), `.env` import and export (0600). `dotenv.ts`: the file format. | `environments`, `secrets` |
| `ci/` | `workflow.ts`: `.github/workflows/ci.yml` from the checks `verify/detect.ts` finds, with every `run:` line from a fixed vocabulary; never over an existing file unless asked. `pr.ts`: pull requests through `gh` (argv only, never a shell): open for a session's branch, checks rolled up to one state, merge. | `session_prs` |
| `deploy/` | `providers/` (`cloudflare`, `vercel`, `fly`, `command`, behind one `types.ts` interface; `exec.ts` runs the CLI with the secrets in the child's environment only). `store.ts`: targets (one per workspace and environment) and the run history; one deploy per target at a time, a rollback is a new run that makes the previous live artifact live again, and every log tail is redacted before it is saved. `release.ts`: the version bump, changelog, commit and tag (`plan` writes nothing). `domains.ts`: a CNAME to the deploy host in the Cloudflare zone (listed, added or updated through the Cloudflare API), and a propagation check over DNS-over-HTTPS. | `deploy_targets`, the deploy runs table |
| `mobile/` | `eas.ts`: `eas-cli` calls as argv, with the environment a provider supplies. `store.ts`: builds and submissions, the poller that follows in-flight builds, and the store listing read from `store/metadata.json`. `preview.ts`: `expo start --tunnel` for Expo Go, one process per project. | `mobile_builds`, `mobile_submissions` |
| `signals/` | `sources/sentry.ts`, `sources/posthog.ts`: pull issues and metrics. `feedback.ts`: the widget's intake (token check, CORS, per-peer rate limit). `sync.ts`: runs every configured source in turn; one failing does not stop the rest. `store.ts`: signals and their triage state. | `signals`, `signal_tokens` |
| `scaffold/golden.ts` | The golden stacks, `saas-next` and `expo-app`, as recipes. Each is a generator plus template files (`scaffold/templates/`) written after it, never over a file the generator made. | none |

**Boot.** `daemon/lifecycle.ts` starts three loops after the HTTP server is up, and stops them on shutdown with the rest:

- **Autopilot** (`startAutopilot`): advances every active run on each `turn_end` and `state` event on the session hub, and on a 30 s fallback timer. A run that was working when the daemon stopped carries on from its recorded task.
- **Scheduler** (`startScheduler`): a ticker that wakes every minute and starts each enabled job whose slot has come. The slot moves before the job starts, so a job that fails does not run again in the same minute. A job that missed its time while the daemon was down runs once when it comes back, not once per missed slot.
- **Mobile poller** (`startMobilePoller`): refreshes in-flight EAS builds, one pass at a time. Shutdown stops it and every Expo preview process.

**How secrets flow.** Values are written with `trb secret set` or `trb secret import`, and listings carry names and times only. Plaintext leaves the store only through `resolveEnv(workspace, env)`, which is called server-side:

- the dev server (`devserver/manager.ts`) injects the `dev` environment when it starts;
- signal sources read `prod` (`daemon/routes/signals.ts`, and `signals_sync` schedules through the same provider);
- deploys (`deploy/store.ts`) get `resolveEnv(ws, env)` for the target's environment, and EAS calls (`mobile/eas.ts`) get `resolveEnv(ws, "prod")`. `lifecycle.ts` plugs both in with `setEnvProvider` at daemon start. The deploy provider only sees the child process's environment (`deploy/providers/exec.ts`), and log tails are redacted before they are saved.

**The one owner-auth exemption.** `POST /api/signals/feedback/:token` is the only `/api` route that skips owner authentication. `server.ts` sends it to `feedbackIntake` before `authenticate` runs (`isPublicSignalsPath`). The token in the path is the credential: `trb signals token --rotate` makes the old one stop working. The handler answers CORS, since the widget runs on the product's own site, and rate-limits per peer. Every other `/api` route, including the signals routes, needs the owner's token or session. The pairing page (`/_pair`) and static files sit outside `/api` and are not part of this rule.

## Decisions worth knowing

- **A turn is a process, a session is a row.** Continuity is the engine's own session id (`--resume`, `codex exec resume`, …), persisted *while the turn runs* so a daemon killed mid-turn can resume it. Engines with no resume, or a refused one, get the brief and previous answer replayed (retried once automatically).
- **Parent stays alive.** A child's final message returns as a tool result inside the parent's turn (`subagent_wait`). Omni's earlier design queued heads as board tasks, ended the lead's run, and re-woke it; that cold-started every head and made the lead rediscover everything. A wait is ONE tool call for the agent however long the heads take (up to `wait_total_sec`, 900s). The daemon holds each request for at most `wait_max_sec` (240s, under the HTTP idle limit), then answers `pending`; the MCP shim asks again with `_resume` and sends progress keepalives, so the model sees no "still running, call again" round trips (each of those was a full inference). While it waits, the lead's view carries `waiting_on` / `waiting_since` and the UI shows it. Verified with real claude: one `subagent_wait` call spanning a 69s wait over four daemon blocks.
- **Identity comes from the connection, not the arguments.** The shim is spawned with `TRB_SESSION`; the daemon trusts that, never a tool argument. A session can only manage children it opened; depth is `parent.depth + 1`.
- **Lead contract goes first in the prompt.** Buried in a context file a capable lead reads it as background and does the work itself; at the top of the turn, with a concrete first tool call to load the deferred tools, it acts on it.
- **The branch tip is the truth about a head's work.** Agents often `git commit` for themselves, leaving nothing for the harness to commit; recorded head SHAs follow the branch, or a closed head's branch would be deleted as "empty".
- **No context files written into your repo.** Role instructions and the lead contract travel in the prompt. The only workspace writes are skills and (cursor) `.cursor/mcp.json`, both restored.
- **Usage limits have per-engine sources.** The composer's hover card stores plan windows in `engine_limits` (`engines/limits.ts`). Claude reports them in a turn's `rate_limit_event`; Grok is read from `_x.ai/billing` on a short `grok agent stdio` session; Cursor's own dashboard calls are read using the token in the Cursor CLI auth file, which is neither logged nor stored; and Codex is read from the newest session rollout under `~/.codex/sessions`. No credential is read for Codex. Grok, Cursor and Codex reads refresh when the limits route is called, at most once every five minutes, including after a miss. OpenCode and Antigravity do not report plan windows.
- **A model id only follows the engine it was chosen for.** A pair's `claude-*` model is never handed to codex.

## Treeboss mode

Opt-in per session (`treeboss_mode` sets the default; `POST /api/sessions/:id/treeboss` or `treeboss` on create sets one session). The three tools (`src/treeboss/tools.ts`) are offered only to a session in treeboss mode: the shim advertises them when the run carries `TRB_TREEBOSS` (set by `buildRunMcpConfig` for such a session), and the daemon refuses them for any other session. The route takes `enabled` and/or `tier` (`tweak|feature|area`, or `null` to clear the override); it answers with `treeboss` and `treeboss_state`. The agent is told the rules once: state a tier (`TREEBOSS_TIER: tweak|feature|area`), read DESIGN.md and `design/tokens.css` before UI work, write specs with the `spec_new` tool and attach them with `spec_attach`, propose a ROADMAP.md item with `roadmap_propose` (it creates the file when missing), update the docs, and for an area research and stop for the operator's pick. `gate.ts` then checks what the turn changed, after the docs check and before verify.

The tier is read from every text block the agent wrote in the turn (`assistantTextOf`: the events of the turn with kind `text`, so a tier line before the tool calls counts), falling back to the final answer. An operator's tier (`tier_source` `operator`) wins over every later declaration until it is cleared; clearing forgets it, and the next declaration sets the tier again. Setting a tier starts the fix attempts over.

The files come from the checkpoints: a turn's changes are the `git diff` between its snapshot and the one before (`checkpointBefore`), so nothing is scanned or snapshotted twice. Four checks, each `pass`, `fail` or `skip` (skip = the tier does not need it, or no UI or source files changed): a hex color added to a UI file that `design/tokens.css` does not define (design); a feature or area change with no attached spec and nothing under `specs/` or `.specify/` (spec: the message names the `spec_new` and `spec_attach` tools); a feature or area change with no change to the roadmap file (roadmap: the message names `roadmap_propose`, which creates the file when it is missing); a feature or area change to source with no doc page or root `*.md` (docs). A broken check goes back as a fix turn, twice at most in a row; the fix turn asks the agent to finish the whole task and to report its outcome, and says which rule does not apply if one does not. Then the gate logs `gate gave up` and stops. A turn that changed nothing is not checked, and `research/` (the area candidates page) is scratch, not built work. Outside git there are no checkpoints, so nothing is checked.

Every turn the gate looks at writes `last_check` (JSON in the store): `{turn_id, at, tier, outcome, checks: [{id, status, detail}]}`, with `outcome` one of `passed`, `fixing`, `gave_up`, `nothing_built` or `not_checked` (no checkpoint, a failed or interrupted turn, or no turn record). It is written before a fix turn starts, so the fix turn and the UI both see it, and a state event is published after it. The session view carries `treeboss_state: {tier, tier_source, attempts, max_attempts, last_check}` while the mode is on for the session, and `null` otherwise. A turn superseded by a newer one writes nothing: that turn writes its own record.

## History

Extracted from the author's own `omni-orchestrator` (its CLI harness, stream parser, worktree manager, Hydra pairs and live subagents), with the organisation, client and marketing scoping removed.
- **Specs are files; the app is a lens.** The database keeps only which session has which path attached. Status, progress and the stepper are derived from the directory on every read, so git history is the history and a hand edit, an agent edit and a click all end up in the same place. A toggle rewrites one character (the one in the brackets) and keeps CRLF and odd spacing byte for byte. Attachments are delivered once, as a short pointer by default; a fresh replay after a refused resume delivers them again. Heads never tick `tasks.md`: their lead does, after merging what really landed.
- **A plan is a file, and the file is the truth.** `plan_submit` makes the daemon write `plans/<date>-<name>.md` (or, at the spec depth, a feature's `plan.md` beside a `spec.md`); the agent stays read-only. The `plans` row keeps metadata (path, version, status, hashes of what was written and approved) plus the structured fields it was submitted with, which only serve a plan from before plan files. Approving reads the file as it is, snapshots it, and rewrites one front matter line; a revision rewrites the same file and appends a changelog entry, and a spec's `spec.md` is left alone once someone else has edited it. Goal turns and handoffs reference the path.
- **The agent names its own session.** A lead's first turn is told to call `session_title` once, before anything else (`src/sessions/title.ts`): the model already has the prompt and the project, so a title costs one short tool call, with no second turn and no second model, and nothing is parsed out of the visible answer. The tool only replaces the *plain* title (the prompt's first line), so an operator's rename or an earlier call always wins, and it is offered on every lead turn in build and plan mode so the tool list (and a resumed conversation's prompt cache) does not change between turns. An engine without MCP, a model that skips the call, ask mode and `session_titles = off` all keep the plain title. The local Ollama model (`src/llm/`) is reserved for work that needs a diff, not a conversation.
- **An architecture discussion cannot be made read-only and also write.** It runs in plan mode (read-only, questionnaire), hands in a plan whose steps are spec-file changes, and the ordinary approve path flips it to build with a message that confines it to `specs/` and `.specify/`; afterwards the daemon puts it back in plan mode and logs a warning if anything else changed. The confinement is the prompt plus that check, not a sandbox.
- **Ask mode is plan mode's lean sibling.** `sessions.mode` is `build | plan | ask`, recorded per turn in `turns.mode` so the cost of ask turns can be summed (`ask_cost_usd`). Its read-only switch is each engine's own (see the README table); on claude the model is only *offered* `Read`/`Glob`/`Grep` (or `Read` plus the two CodeGraph tools) through `--tools`, which is both the enforcement and the saving, because the other tools' schemas are never sent. `startTurn` skips what a question does not need: skills, the operator's MCP servers and the subagent shim (`buildRunMcpConfig({ ask: true })` keeps only CodeGraph), agent and pair preambles, the CodeGraph hint (the ask preamble says it), a worktree, and re-sending attachments already delivered. A new ask session picks its cheap model in the create route (`askStartModel`), not in `createLead`, so a pair's or an agent's model and an explicit choice always win; an existing session keeps its model unless `ask_model_override` is on, because a model switch invalidates the prompt cache. "Save as doc" is `sessions/askdoc.ts` over the docs module's `createPage`: it writes only on an explicit POST.
- **File mentions in chat are links, but only to files that exist.** `FileLinkScope` (`web/src/features/agent/FileLinks.tsx`) wraps a thread and loads the file list of the root the session works in: the workspace for a normal session (so a link opens the same tab as the file tree), the session's own directory for a worktree session. `file-links.ts` (pure, tested in `tests/web/file-links.test.ts`) turns inline code, plain text and markdown links (`path`, `path:12:5`, `path#L12`, absolute paths inside the working directory, `file://`) into `<file-link>` elements through a remark step; a name only links when exactly one real file matches it, and files the agent's own Write/Edit calls named count even before the list refreshes. A click is `openTab({ kind: "file", … line })`. Outside a scope (docs, design, transcripts) `Markdown` is unchanged. `scripts/ui-filelinks.ts` drives it in a browser.
- **Evidence is two settings, both on by default, and one index, not a new engine feature.** `evidence` adds ten tools (`src/evidence/defs.ts`, run by `tools.ts` in the daemon like the browser's) to the `trb` MCP shim through `TRB_EVIDENCE`, which also makes the shim appear when nothing else would; `rea_mcp` adds a separate stdio server named `rea` in `buildRunMcpConfig`. Both are decided per turn in `startTurn` (never in ask mode) and announced once per conversation next to the CodeGraph hint. The project is always the calling session's `base_cwd`, never an argument, so an agent cannot read or cite another project's evidence; routes and tools both go through `getEvidence(id, workspace)`. Storage is files plus an index row in the trb home, written files-first so a row never points at nothing. Capture reads the page the agent browser already has open (`capture.ts`) and keeps Resource Timing, not headers or bodies. Captured text is served only as sandboxed `text/plain`. Investigations are one table and their runs a second (`investigation_runs`, one row per run, linked to its investigation and its session), and findings are notes with a `finding` column and a status, so the same files and index serve both; `investigation_id`, `finding`, `finding_status` and `source` are added with `addColumn`, so an older file opens. A run is an ordinary lead session with a prompt built per target kind; its status is read from that session, not stored twice. The build brief is `buildPrompt` in `src/evidence/investigations.ts`, and the web's "Build selected" only opens it in a new composer and PATCHes the findings to `planned`. An investigation's kind defaults to `auto`: `detect.ts` works it out from the target alone (bounded reads, no recursion) and stores it with its reason; `readiness.ts` checks what REA needs (shallow by default, deep with REA's own `rea doctor --json` for `trb doctor` and Check again); and `reaEnv()` gives the `rea` process the absolute paths of the engines it found, each only when unset.
